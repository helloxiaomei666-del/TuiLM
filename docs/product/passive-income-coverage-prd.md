# TuiLM 综合退休率与被动收入覆盖率 PRD

> 文档状态：待项目负责人确认后冻结
>
> 产品范围：TuiLM 的 Web Demo、微信小程序与 H5 `retire-quiz` 的统一退休准备度、被动收入覆盖率与生息资产口径
>
> 本 PRD 不授权真实 SDK、真实行情、自动交易或投资建议能力。

## 1. 背景与问题

TuiLM 当前的“退休率 / 退休进度”在三端没有统一定义，容易使用户把资产存量、资产上涨和可用于生活的现金流混为一谈。

- H5 `retire-quiz` 已有 `cashflowRetirementRate`，以稳定被动收入相对目标月生活成本的比例表达，最接近本 PRD 的方向。
- 微信小程序已有 `passive-income-model`，能够区分完全被动、半被动、未来收入和当前收入；但首页主视觉仍以资产进度表达“退休进度”。
- Web Demo 当前主要以 `currentAssets / target` 和未来资产模拟表达进度，工资、副业、支出与历史收益假设会影响预计达成时间。

资产存量仍然有价值，但它不能自动等同于“今天不靠工资能否支付生活开销”。本 PRD 的目标是冻结一个可跨端复用的综合退休准备度框架：以被动收入覆盖率为最核心的二级指标，同时将现金安全垫、生息资产、资产进度、保障账户和拖累项目拆分展示、共同解释。

## 2. 总退休率 / 退了吗指数

### 2.1 一级定义

TuiLM 的“退休率”不是单一资产进度，也不是单一被动收入覆盖率，而是一个综合退休准备度指标，名称为“总退休率 / 退了吗指数”。

> 总退休率 / 退了吗指数：一个人在不依赖主动劳动收入的前提下，依靠稳定现金流、可动用资产、生息资产、保障账户和低拖累结构，维持目标生活水平的综合完成度。

该指数用于回答“为什么还没退、哪一项最需要补齐”，而不是替代被动收入覆盖率。被动收入覆盖率仍是核心现金流事实，必须单独、显著、可追溯地展示。

### 2.2 指数边界

- 总退休率是 0 至 100 分的解释型准备度指数，不是收益率、概率承诺或退休资格认定。
- 指数不将工资、兼职、一次性收入、资产浮盈或出售本金当作被动收入。
- 指数中的各二级指标必须保留独立原始值、数据来源、计算状态和解释文案；不得以总分掩盖被动收入不足或重大拖累。
- 权重是 V1 产品口径，后续可以经负责人确认后集中调整；页面不得自行定义或覆盖权重。

## 3. 指标层级与 V1 权重建议

### 3.1 指标层级

| 层级 | 指标 | 作用 |
| --- | --- | --- |
| 一级指标 | 总退休率 / 退了吗指数 | 汇总退休准备度，并解释最主要的优势与短板。 |
| 二级指标 | 被动收入覆盖率、现金安全垫、生息资产质量、总资产进度、保障账户完成度、拖累项目惩罚 | 构成或影响一级指数；每项必须单独展示。 |
| 三级明细 | 房租净收入、股息/分红、红利 ETF 分红、债券票息、存款利息、货币基金收益、养老金/年金、社保、医保、商业保险、公积金、房贷、车贷、消费贷、赡养压力、高固定支出、非生息资产占比、高风险资产暴露 | 用于计算、解释和定位改善方向。 |

### 3.2 V1 权重建议

V1 采用以下可集中配置的权重，用于帮助用户理解“自己为什么还没退”，不是最终或永久权重：

| 二级指标 | V1 权重 / 影响 |
| --- | --- |
| 被动收入覆盖率 | 40% |
| 现金安全垫 | 15% |
| 生息资产质量 | 15% |
| 总资产进度 | 15% |
| 保障账户完成度 | 15% |
| 拖累项目惩罚 | 最多扣 20 分 |

建议的 V1 计算表达为：

```text
总退休率 / 退了吗指数 = clamp(
  0.40 × 被动收入覆盖率得分
  + 0.15 × 现金安全垫得分
  + 0.15 × 生息资产质量得分
  + 0.15 × 总资产进度得分
  + 0.15 × 保障账户完成度得分
  - 拖累项目惩罚分,
  0,
  100
)
```

所有正向二级指标先转换为 0 至 100 的得分；其转换阈值、数据缺失策略和拖累项分档必须由统一核心计算配置提供。拖累项目总扣分最高为 20 分，不能使单项扣分或页面文案暗中改变权重。

### 3.3 二级指标含义

| 二级指标 | 定义 | 回答用户的问题 |
| --- | --- | --- |
| 被动收入覆盖率 | 稳定月被动收入 ÷ 月必要支出 | 不靠工资时，每月自动进账的钱够不够覆盖基础生活？ |
| 现金安全垫 | 可快速动用现金 ÷ 月必要支出 | 如果收入中断，可以撑几个月？ |
| 生息资产质量 | 生息资产占比、收入稳定性、来源分散度及是否依赖出售本金的综合得分 | 资产是否能持续产生现金流？ |
| 总资产进度 | 当前净资产 ÷ 目标退休资产 | 资产本金距离长期目标还有多远？ |
| 保障账户完成度 | 社保、医保、商业保险、公积金、养老金和年金等保障构成的风险防线得分 | 遇到疾病、意外、失业或长期养老支出时，计划会不会被打穿？ |
| 拖累项目惩罚 | 房贷、车贷、消费贷、信用卡债务、高固定支出、赡养压力、高风险资产暴露及流动性差资产占比过高造成的扣分 | 什么正在拖慢退休进度？ |

保障账户缺失不应被简单视为零保障或直接归零；系统应显示“信息不足/待补充”，并按统一保守规则降低综合得分，同时明确降低原因。

## 4. 被动收入覆盖率：核心二级指标

### 4.1 核心公式

```text
退休率（被动收入覆盖率） =
  稳定可使用的月被动收入 ÷ 月必要支出 × 100%
```

对应的系统指标名为：

```text
passive_income_coverage_rate =
  monthly_stable_passive_income / monthly_essential_expense
```

当月必要支出缺失、为零或无效时，核心退休率必须显示“暂不可计算”，不得用资产目标、工资结余或任意默认值替代分母。

### 4.2 面向用户的解释

> 不靠工资时，每月稳定产生的钱，能覆盖基础生活开销的比例。

该指标回答的是当前现金流覆盖能力，不是辞职建议、收益承诺或投资建议。比率达到或超过 100% 也不自动代表可以立即退休，仍需同时观察安全垫、收入稳定性、通胀、医疗和家庭责任。

### 4.3 核心边界

- 生息资产本金默认不卖出；只计算资产自然产生且当前可使用的现金流。
- 核心指标只使用稳定、净额、可持续、无需持续劳动、非一次性、非出售本金所得的收入。
- 资产估值、资产浮盈和总资产进度是辅助指标，不得直接进入核心退休率的分子。
- 核心退休率保存原始比率；UI 进度条最高显示 100%，数值文本可显示超过 100%。

## 5. 被动收入覆盖率的指标与辅助指标

| 指标 | 系统字段 | 定义与用途 |
| --- | --- | --- |
| 核心退休率 / 被动收入覆盖率 | `passive_income_coverage_rate` | 稳定可使用月被动收入除以月必要支出，是综合退休率中权重最高的二级指标，也是首页首要现金流事实。 |
| 稳定月被动收入 | `monthly_stable_passive_income` | 所有满足核心纳入条件的收入来源月净额之和。 |
| 月必要支出 | `monthly_essential_expense` | 退休后维持基础生活必须持续支付的月支出；须独立录入和解释。 |
| 资产安全垫 | `asset_safety_runway_months` | 可即时使用的流动资产除以当前必要月支出/持续刚性支出，用于短期韧性。 |
| 总资产进度 | `total_asset_progress` | 净资产或可投资资产相对单独定义的目标资产的进度；只作辅助观察。 |
| 收入稳定性等级 | `income_stability_level` | 对每笔来源及聚合结果提示稳定程度和数据完整性，不以权重虚增核心收入。 |
| 被动收入缺口 | `passive_income_gap` | `max(0, 月必要支出 - 稳定月被动收入)`；达到覆盖后展示盈余。 |

辅助指标可包括半被动收入、劳动依赖率、未来保障支持、总资产、净资产、资产估值变化和目标资产路线。它们不得替代核心退休率。

## 6. 纳入核心退休率的收入

以下收入类型可以进入核心退休率：房租净收入、股息/分红、红利 ETF 分红、债券票息、存款利息、货币基金收益、已实际领取的养老金/年金、版税/授权收入、经营性被动收入和其他可持续现金流。

每一笔来源必须同时满足以下条件：

1. **当前实际可用**：已实际到账或按已发生结算周期可确认，不是未来预测。
2. **净额**：已扣除该收入直接相关的税费、费用、维护成本和持续性偿债支出。
3. **可持续**：不是一次性、临时性或偶然性所得，并具有可解释的持续依据。
4. **无需持续劳动**：不以持续兼职、接单、交易或日常经营劳动为前提。
5. **非出售本金**：不来自卖出股票、基金、房产、债券本金或提取本金。
6. **来源唯一**：不能与持仓产生的收入流、独立收入流或其他资产重复计入。
7. **稳定性合格**：稳定性不足、数据不足或处于未来状态时，仅可辅助展示。

建议使用 `high`、`medium`、`low`、`unverified` 四级稳定性。核心纳入阈值和历史期数由后续冻结的数据契约明确；在阈值未满足前，系统必须选择保守排除，而非自动纳入。

## 7. 不纳入核心退休率的项目

以下项目必须排除出核心退休率：

- 工资；
- 兼职收入；
- 一次性奖金；
- 股票浮盈；
- 基金浮盈；
- 房产涨价；
- 短线交易收益；
- 卖出资产获得的钱；
- 未来预计养老金；
- 尚未到账的预期分红；
- 临时补贴或红包。

这些数据可作为主动收入、资产表现、未来支持、半被动收入或情景测算的辅助信息展示，但页面和计算结果不得把它们纳入 `monthly_stable_passive_income` 或 `passive_income_coverage_rate`。

## 9. 计算规则

1. 生息资产本金默认不卖出；本金不进入核心退休率分子。
2. 只计算资产自然产生的、当前实际可使用的现金流。
3. 资产估值、净值上涨、房产涨价和未实现浮盈不等于退休率。
4. 负债、税费、维护成本、空置准备和直接经营成本应从对应收入中扣除。
5. 同一收入来源必须有唯一来源键；持仓产生的现金流与独立收入流不得重复计入。
6. 稳定性不足、未来状态、尚未到账、依赖持续劳动或一次性收入，进入辅助展示而非核心退休率。
7. 月收入换算仅对定义明确的周期进行。无法可靠换算的非固定收入不得猜测为稳定月收入。
8. 原始比率可大于 100%；数值显示应保留真实值，UI 进度条最多显示 100%。
9. 总资产进度、安全垫和未来资产路线必须使用独立字段与文案，禁止借用“退休率”名称。
10. 总退休率只可由统一配置的二级指标得分和拖累项目惩罚计算；被动收入覆盖率、总资产进度和安全垫不得互相替代。
11. 社保、医保、商业保险、公积金、养老金和年金应作为保障账户完成度的明细；其中仅实际领取的养老金/年金可进入被动收入覆盖率。

## 10. 页面改造建议

### 10.1 首页统一表达

首页应同时展示总退休率 / 退了吗指数、被动收入覆盖率、现金安全垫、最大拖累项和一句话解释。推荐文案结构如下：

> 你的总退休率：46%。其中，被动收入已覆盖 28% 的必要支出；现金安全垫约 10.5 个月。当前主要拖累项是房贷和非生息资产占比偏高。

总退休率的卡片必须可进入二级指标明细；被动收入覆盖率必须保留独立数值和分子/分母说明，不能仅作为总分中的不可见权重。

### 10.2 小程序

- 首页首要指标展示总退休率 / 退了吗指数，同时在首屏明确展示核心退休率/被动收入覆盖率及其分子、分母和纳入范围。
- 原“退休进度”改名为“总资产进度”。
- 在完整负债模型落地前，将“净资产”暂改为“可投资资产”。
- 新增“生息资产 / 被动收入”录入入口，支持资产关联、收入状态、净额、稳定性和排除原因。
- 展示房租、分红、利息等收入来源对稳定月被动收入的贡献占比，并可查看未纳入原因。
- 展示现金安全垫、保障账户待补充项和最大拖累项；总分必须能下钻到每项得分、扣分和原因。
- 将资产路线保留为辅助模块，明确其是资产目标路线而不是核心退休率。

### 10.3 Web Demo

- 补齐收入流、月必要支出和收入稳定性字段。
- 在总览中区分被动收入覆盖率、资产安全垫和总资产进度。
- 增加综合退休率、保障账户完成度和拖累项目解释，但权重与得分只能使用统一核心配置。
- 保留资产目标路线与退休时间模拟，但改名并说明其假设；不得把资产进度直接称为退休率。
- 保障账户中的未来预计收入与当前实际领取收入必须分层展示。

### 10.4 H5 `retire-quiz`

- 将“目标月生活成本”统一为“月必要支出”，并提供迁移映射与口径说明。
- 为被动收入补充稳定性、当前到账、是否依赖劳动、是否出售本金及来源唯一性字段。
- 维持轻量测算体验：复杂资产明细可采用渐进展开，不要求用户首次填写全部信息。
- 保留总资产进度与安全垫的辅助价值，但避免与核心退休率使用相同名称或状态文案。
- 首屏可以展示简化后的总退休率与主要短板，但须让用户可查看被动收入覆盖率、资产进度和保障/拖累解释的分项结果。

## 11. 测试验收标准

以下为后续实现前必须先写入失败测试的验收规则：

1. 工资、兼职、一次性收入不进入核心退休率。
2. 股票浮盈、房产涨价、卖出资产所得不进入核心退休率。
3. 房租必须按净收入计算，并扣除配置的空置、税费、维护和持续偿债成本。
4. 养老金/年金只有实际领取部分可进入核心退休率；未来预计金额必须排除。
5. 同一来源不能通过资产和独立收入流重复计入。
6. 稳定性不足、非当前到账或劳动依赖收入不进入核心退休率。
7. 三端在同一输入下得到相同的核心退休率、月稳定被动收入、月必要支出和缺口。
8. 旧数据迁移后不得把资产估值、历史资产余额或默认预期收益自动计入被动收入。
9. 月必要支出无效时，核心退休率必须不可计算。
10. 原始比率超过 100% 时，数值正确保留而 UI 进度条不超过 100%。
11. 总退休率可由各二级指标按集中配置的权重加权得出，并受拖累项目惩罚影响。
12. 被动收入覆盖率不能被资产进度、安全垫或总退休率替代；同一数据下三者必须分别可解释。
13. 拖累项目必须能产生可追溯扣分，且总扣分不超过 V1 上限 20 分。
14. 保障账户缺失不能直接归零，但应按统一保守规则降低综合退休率并说明信息不足。
15. 权重变更必须只发生在集中配置或统一核心模型中，不得散落在页面代码中。

## 12. 非目标

本 PRD 不做以下事项：

- 真实 SDK 接入；
- 真实行情请求；
- 自动读取券商账户；
- 自动估算全部分红；
- 投资建议；
- 收益承诺；
- 自动交易；
- 商业化行情服务。

本 PRD 也不将任何第三方行情、账户或 SDK 能力作为核心退休率计算的前置条件。第一阶段可基于用户手动输入和本地数据完成口径统一。

## 13. 实施路线

1. **阶段 1：冻结 PRD。** 项目负责人确认本文件中的综合退休率定义、V1 权重、核心纳入条件、月必要支出口径、稳定性阈值和迁移原则。
2. **阶段 2：写失败测试。** 先建立统一模型的边界、去重、迁移、二级指标、拖累扣分和跨端一致性测试，不修改现有公式。
3. **阶段 3：统一核心计算模型。** 建立平台无关的纯计算契约与集中权重配置，输出总退休率、二级指标、来源明细、扣分原因和辅助指标。
4. **阶段 4：小程序先落地。** 完成收入流录入，以及首页“总退休率、核心退休率、资产安全垫、总资产进度、最大拖累项”的可解释展示。
5. **阶段 5：迁移 Web Demo。** 接入相同契约，保留但重命名资产路线和资产目标进度。
6. **阶段 6：轻量调整 H5。** 使用相同核心口径，补齐必要字段，同时保持快速自测体验和分项说明。
7. **阶段 7：再评估星耀数智能否辅助估值或分红数据。** 该评估必须单独立项、满足授权和安全门禁，不影响核心模型对手动录入的可用性。

## 14. 冻结后的产品验收口径

PRD 冻结后，所有页面、接口、测试、示例数据和说明文案均应以本文件的综合退休率和被动收入覆盖率定义为准。任何新增资产类型或收入来源必须先声明：是否属于稳定可使用现金流、如何计算净额、是否依赖劳动、如何判定稳定性，以及在不满足条件时的排除原因。任何新增保障项或拖累项必须声明其二级指标归属、得分/扣分依据和数据缺失时的保守处理方式。
