# 退了吗项目计划

## 产品定位

退了吗是一个个人财富计算器和资产行情记录工具。

核心问题：

> 今天，您退休了吗？

产品只做记录、计算和解释，不做投资建议，不推荐金融产品，不承诺收益，不提供自动交易能力。所有表达必须克制、可解释、可删除，避免制造焦虑。

## 当前状态

当前版本是静态 Web MVP，核心文件包括：

- `index.html`：页面结构。
- `styles.css`：桌面、移动端和手机外框预览样式。
- `app.js`：页面状态、DOM 渲染和交互。
- `calculation-core.js`：可复用纯计算核心。
- `tests/calculation-core.test.js`：核心计算最小测试。

已经具备：

- 总览页：当前净资产、每月可投入、回测收益率、工资增长率、预计退休日期。
- 资产页：现金、基金/股票、债券、商品四类持仓。
- 资产录入：名称、代码、持有数量、成本价、当前价、截图导入占位。
- Mock 行情刷新：刷新当前价、计算今日盈亏、影响退休进度。
- OCR 占位：按资产类型模拟识别，先进入待确认结果卡片，用户确认后才回填表单并允许保存。
- 保障账户：养老金、公积金、补充公积金、企业年金、职业年金，不计入可投资资产，但参与退休缺口、预计月领取和房贷现金流支持测算。
- 路线图：未来资产路径、目标线、达成点、年份检查、对比方案。
- 拖累项：可记录房贷、车贷、医疗、其他类支出，并参与退休时间模拟。
- 本地保存：持仓、拖累项、保障账户存入当前浏览器 `localStorage`。
- 数据删除：提供一键清除本地数据入口。
- 工程基础：已初始化 Git，新增 `.gitignore`，临时 tunnel 文件已移入 `.runtime/`，并新增 `start-demo.ps1` 用于稳定启动和停止本地服务。

仍然缺：

- 真实行情服务。
- 真实 OCR 后端。
- 用户账号和跨设备数据存储。
- 可上线的隐私政策、用户协议、免责声明页面。
- 真实环境下的浏览器 UI 自动化检查。
- 微信小程序或 iOS 原生工程。

## 近期优先级

### 1. 稳定 Web MVP

目标：让当前 Demo 变成可持续迭代的 MVP，而不是一次性页面。

已完成：

- 初始化 Git。
- 添加 `.gitignore`。
- 移走 `cloudflared.exe`、日志等临时运行文件。
- 同步 README 和项目计划。
- 拆出计算核心。
- 补核心计算最小测试。
- 增加本地数据清除入口。
- 增加一键启动脚本，启动后验证 `index.html?preview=phone` HTTP 200。
- 给 OCR 模拟流程增加“待确认结果”界面，未确认结果不回填、不保存。

还要做：

- 加浏览器冒烟检查，至少验证主页面无控制台错误、移动端 tab 可切换、行情刷新可用。
- 给 `app.js` 继续拆分页面渲染模块，降低单文件体积。

低风险拆分顺序：

1. `storage`：抽出持仓、拖累项、保障账户的 load/save/clear；验收方式是 localStorage key 不变，清除数据、刷新页面、恢复示例数据都正常。
2. `tabs-ui`：抽出 `setActivePage`、移动端 tab 状态、总览页输入区显示规则；验收方式是五个 tab 只有当前页面可见，“输入你的数据”只在总览页显示。
3. `asset-rendering`：抽出资产汇总、持仓列表、分类展开、删除和 mock 行情刷新渲染；验收方式是添加/删除资产、刷新行情后总资产和今日变化同步更新。
4. `security-rendering`：抽出保障账户表单读取和渲染；验收方式是保障账户更新后只影响保障支持文案，不计入可投资资产。
5. `route-rendering`：抽出路线图 SVG 和年份选择；验收方式是滑动/点击年份后检查器更新，tab 切换回来图表不空白。
6. `drag-rendering`：抽出拖累项表单、列表和场景建议；验收方式是添加/删除拖累项后每月可投入和预计日期同步变化。

### 2. 收敛小程序 MVP

短期建议优先微信小程序，因为当前 Demo 已经是移动端信息架构，迁移成本低于直接做完整 iOS。

当前进展：

- 已创建 `wechat-miniapp/` 工程骨架，可导入微信开发者工具。
- 已迁移计算核心、本地存储、默认数据、格式化工具。
- 已完成总览、资产、保障、路线、拖累项五个 tab 的 MVP 页面。
- 已补隐私与免责声明页面入口，强调本地存储、OCR 确认和非金融建议边界。
- 已补 Node 测试覆盖小程序工程结构、计算、资产、拖累项、保障账户、路线模型和 OCR mock。

小程序 MVP 页面：

- 总览页。
- 资产页。
- 路线图页。
- 拖累项/报告页。

第一版数据结构：

- userProfile：年龄、目标金额、工资、生活支出、副业收入。
- holdings：资产类型、标的类型、名称、代码、持有数量、成本价、当前价、当前市值、今日盈亏、更新时间。
- manualDrags：类型、标题、每月金额、说明。
- securityAccounts：养老金、公积金、补充公积金、企业年金、职业年金。
- calculationSnapshot：每次计算输出的进度、预计日期、关键解释。

详细字段见 `docs/wechat-mvp-data-model.md`。

### 3. 真实行情服务

接入顺序建议：

1. 黄金价格。
2. 基金净值日更。
3. A 股和 ETF 基础行情。
4. 债券基金净值。
5. 港股、美股、汇率和更多商品。

第一版只做用户点击刷新，不做自动交易，不做买卖建议。

### 4. OCR 与确认流程

真实 OCR 必须满足：

- 用户主动选择截图。
- 识别结果进入待确认状态。
- 用户可编辑识别字段。
- 用户确认后才保存。
- 未确认结果不持久化。

支持字段：

- 名称。
- 代码。
- 市值。
- 成本。
- 持有份额或持有数量。
- 当前价格或净值。

### 5. 合规与数据安全

上线前必须补齐：

- 隐私政策。
- 用户协议。
- 免责声明。
- 数据删除入口。
- 数据导出说明。
- 敏感数据存储策略。

禁止能力：

- 买入建议。
- 卖出建议。
- 加仓/减仓建议。
- 推荐基金、股票或策略。
- 收益承诺。
- 自动登录第三方账户。
- 未授权抓取行情或账户数据。

隐私政策与免责声明草案见 `docs/privacy-and-disclaimer-draft.md`。

## iOS 方向

iOS App 暂不建议直接完整复刻当前 Demo。更稳妥的路径是：

1. 建 SwiftUI 工程。
2. 迁移计算核心的数据模型和测试样例。
3. 先做总览页。
4. 再做资产页。
5. 最后做路线图和 OCR 流程。

这样可以避免在原生端重复堆复杂表单和图表，先验证核心体验。
