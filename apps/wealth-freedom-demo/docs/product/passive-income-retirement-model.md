# 《退了吗》被动收入与现金流退休率模型设计文档

> 文档状态：产品与技术设计决策稿
> 日期：2026-06-24
> 本阶段范围：只定义模型、数据契约、页面方向、测试方案和落地顺序，不修改业务代码、测试、配置或现有退休公式。

## 1. 设计背景

《退了吗》当前是一套“资产记录 + 退休目标测算”工具。现有模型主要回答：

> 我距离目标资产还差多少钱，以及按当前储蓄和历史回测假设还需要多久？

这个问题仍然有价值，但不足以独立解释退休能力。资产总额描述的是存量；用户每月能否在不依赖劳动收入的情况下支付生活成本，描述的是现金流覆盖能力。两者相关，但不能互相替代。

本次产品重构的方向不是删除原模型，也不是给资产多加一个字段，而是形成双层解释：

1. **现金流层为主**：当前实际收到的完全被动收入，能覆盖多少目标生活成本。
2. **资产层为辅**：当前资产积累到目标资产的多少，短期可动用资产还能支撑多久。

阶段 A 的自动化测试、小程序 validator、preflight 和微信真机基线仍是当前工程前提。本设计不能打断验收，不能借机进行目录重构，也不能改变现有退休时间模拟。

### 1.1 本文要回答的问题

- 被动收入是否应该成为《退了吗》的新核心解释维度。
- 现金流退休率、资产退休率、安全垫月数和劳动依赖率如何共存。
- 完全被动、半被动、主动、一次性和未来支持如何分账。
- 未来数据、函数、页面和测试应该采用什么契约。
- 新模型如何与当前小程序和 Web Demo 共存，而不破坏现有基线。

### 1.2 设计原则

- **当前实际优先于未来预期**：只把当前已经发生、可用于生活的现金流计入主指标。
- **严格口径优先于激励性数字**：宁可低估当前退休现金流，也不把需要劳动或尚未实现的收益包装成被动收入。
- **分层而不是混合**：完全被动收入、半被动收入、资产存量和未来保障分别展示。
- **可解释而不是伪精确**：稳定性用于提示风险，不用主观权重把不同收入混成一个“精确分数”。
- **兼容而不是推倒重来**：保留现有公式、字段和页面结构，在后续阶段增量接入。
- **中立而不是建议**：不推荐资产、不预测回报、不把任何结果解释为辞职或买卖依据。

## 2. 核心理念

新的产品核心问题是：

> 你的资产和已形成的被动收入，每个月已经替你承担了多少目标生活成本？

主指标定义为：

```text
现金流退休率 = 当前月完全被动收入 / 目标月生活成本
```

当 `targetMonthlyLivingCost` 有效且大于 0 时使用目标月生活成本；未填写时回退到当前月生活成本 `monthlyLivingCost`。页面必须显示本次采用的分母，不能让用户误以为两个口径相同。

例如：

```text
当前月完全被动收入：800 元
目标月生活成本：6,000 元
现金流退休率：13.3%
劳动依赖率：86.7%
```

对应产品表达：

> 你的资产和已形成的被动收入，目前每月约能替你承担 13.3% 的目标生活成本。剩余 86.7% 仍需要劳动收入或其他资金来源支持。

“资产替你承担”是一种面向用户的简化表达。模型实际计算的是当前已确认的完全被动收入，不把资产市值本身、预期涨幅或预计分红直接视为收入。

### 2.1 严格双层收入模型

本文采用以下已确认口径：

- 主现金流退休率只计入**完全被动收入**。
- 半被动收入单独汇总为 `monthlySemiPassiveIncome`。
- 可展示“含半被动收入覆盖率”，但它只是补充观察值，不进入主指标和退休状态分级。
- 主动收入和一次性收入不进入任何被动收入覆盖率。
- 尚未开始领取的养老金、年金和预期投资收益只作为未来支持或背景信息。

### 2.2 不采用加权退休率

本阶段不按“稳定性 80%”“劳动依赖 60%”等主观权重折算收入。原因是：

- 权重缺乏统一、可审计的依据。
- 用户容易把复杂权重误认为金融预测模型。
- 调整权重会改变退休状态，但不代表真实现金流发生变化。
- 稳定性、期限和劳动依赖更适合成为风险标签和警告，而不是修改到账金额。

## 3. 为什么退休率不能只看资产总额

资产退休率回答“攒到了多少”，现金流退休率回答“当前能承担多少生活”。两者差异如下：

| 维度 | 资产退休率 | 现金流退休率 |
| --- | --- | --- |
| 分子 | 当前资产存量 | 当前月完全被动收入 |
| 分母 | 目标资产金额 | 目标月生活成本 |
| 主要问题 | 资产积累进度如何 | 生活成本覆盖能力如何 |
| 优势 | 易理解，能延续现有模型 | 更接近退休后的月度支付能力 |
| 局限 | 不反映流动性和当前现金流 | 不反映本金规模、资产升值和短期缓冲 |
| 产品角色 | 辅助指标 | 第一核心指标 |

只看资产总额会产生至少五类误判：

1. 资产有市值，但不能直接支付当月生活成本。
2. 资产可能流动性低、出售周期长或存在处置成本。
3. 资产价格可能波动，当前市值不等于可持续收入。
4. 达到目标资产后仍可能依赖持续卖出资产。
5. 两个资产总额相同的人，实际现金流和生活成本可能完全不同。

反过来，只看现金流也不充分。租金、股息或版权收入可能中断；没有安全垫的人即使当月覆盖率较高，也可能缺乏短期韧性。因此产品必须同时保留资产退休率和安全垫月数。

## 4. 四率模型设计

### 4.1 现金流退休率：第一核心指标

```text
cashflowRetirementRateRaw = monthlyPassiveIncome / denominatorMonthlyLivingCost
```

其中：

```text
denominatorMonthlyLivingCost =
  targetMonthlyLivingCost > 0
    ? targetMonthlyLivingCost
    : monthlyLivingCost > 0
      ? monthlyLivingCost
      : unavailable
```

规则：

- `monthlyPassiveIncome` 只包含当前实际收到、可用于生活、分类为 `passive` 且通过纳入校验的收入。
- 预期收益、未实现涨幅、预计分红和尚未领取的保障收入不计入。
- 半被动收入不计入主指标。
- 原始值允许超过 100%。
- 进度环显示值为 `min(rawRate, 1)`，但数值文本显示真实比例。
- 超过 100% 时另行展示月现金流盈余。
- 分母缺失或小于等于 0 时返回“暂不可计算”，不能返回 0%、100% 或 `Infinity`。

它位于首页第一位，因为它直接回答：“当前有多少生活成本已经不再依赖工资？”

### 4.2 资产退休率：保留的辅助指标

概念公式：

```text
资产退休率 = 当前纳入退休测算的资产 / 目标退休资产
```

现有项目实际使用 `progressFromAssets(currentAssets, target)`。在未引入完整负债余额模型前，不应把现有 `currentAssets` 对外宣称为严格意义上的“净资产”。本阶段保持现有公式和口径，不做重命名式迁移。

资产退休率应保留，原因包括：

- 本金是形成未来现金流和应对不确定性的基础。
- 尚未产生现金流的资产仍具有真实价值。
- 现有退休时间模拟、目标缺口和用户历史数据均依赖它。
- 它可以解释“本金积累进度”，但不再独占“退休率”概念。

现金流退休率与资产退休率可能出现四种组合：

| 资产退休率 | 现金流退休率 | 解释 |
| --- | --- | --- |
| 低 | 低 | 本金和现金流均在起步阶段 |
| 高 | 低 | 资产较多，但当前现金流形成不足或资产偏非现金流型 |
| 低 | 高 | 现金流覆盖较强，但本金和安全缓冲可能有限 |
| 高 | 高 | 存量、现金流与缓冲均较成熟，仍需检查风险与稳定性 |

### 4.3 安全垫月数：短期韧性指标

```text
runwayMonths = liquidAssets / currentRequiredMonthlyOutflow
```

`currentRequiredMonthlyOutflow` 应由调用方按当前生活场景传入，原则上包括当前基本生活成本和仍需持续支付的房贷、车贷、其他固定还款及长期拖累项。它与现金流退休率使用的“目标退休生活成本”不是同一分母。

可动用资产的保守定义：

- 已有现金和可随时动用的存款。
- 用户明确标记为紧急情况下可动用、流动性高的资产。
- 不默认计入自住房、未领取养老金、企业/职业年金、低流动性房产或其他锁定资产。
- 不因为某项资产“可能卖出”就自动计入。

产品表达：

> 如果当前劳动收入中断，你的可动用资产约能覆盖 8.5 个月的当前必要支出。

该指标对年轻用户尤其重要，因为在本金和被动收入尚低时，6–12 个月安全垫往往比遥远的退休资产目标更可操作。这里的 6–12 个月是产品路线参考区间，不是个性化财务建议。

### 4.4 劳动依赖率：主指标的反向解释

```text
laborDependenceRate = max(0, 1 - cashflowRetirementRateRaw)
```

规则：

- 现金流退休率为 13.3% 时，劳动依赖率为 86.7%。
- 现金流退休率超过 100% 时，劳动依赖率显示 0%，不显示负数。
- 现金流退休率不可用时，劳动依赖率同样不可用。
- 半被动收入不降低主劳动依赖率；可在旁边展示补充口径。

它比单独显示退休率更直接，但必须采用中性文案，避免制造焦虑。推荐：

> 当前目标生活成本中，约 86.7% 仍需要劳动收入或其他资金来源支持。

不推荐：

> 你还有 86.7% 的生活被工作绑架。

### 4.5 补充指标

以下指标可以展示，但不属于“四率”主面板：

```text
含半被动收入覆盖率 =
  (monthlyPassiveIncome + monthlySemiPassiveIncome) / denominatorMonthlyLivingCost

被动收入缺口 = max(0, denominatorMonthlyLivingCost - monthlyPassiveIncome)

现金流盈余 = max(0, monthlyPassiveIncome - denominatorMonthlyLivingCost)
```

## 5. 数据模型设计

### 5.1 用户目标模型

```js
userProfile = {
  targetAssetAmount: 3000000,

  monthlyLivingCost: 6000,
  targetMonthlyLivingCost: 8000,

  currentMonthlySalary: 9000,
  currentMonthlySideIncome: 1000,

  retirementMode: "cashflow_first"
}
```

| 字段 | 含义 | 规则 |
| --- | --- | --- |
| `targetAssetAmount` | 资产退休率分母 | 对应现有 `target`；本阶段不修改现有公式 |
| `monthlyLivingCost` | 当前月基本生活成本 | 现金流分母的回退值，也是当前安全垫支出的组成部分 |
| `targetMonthlyLivingCost` | 用户期望退休后的月生活成本 | 有效时优先作为现金流退休率分母 |
| `currentMonthlySalary` | 当前月工资 | 主动收入，不计入被动收入 |
| `currentMonthlySideIncome` | 当前月副业收入 | 默认主动收入；不能因名称是“副业”自动视为半被动 |
| `retirementMode` | 产品解释模式 | 首期固定为 `cashflow_first`，为兼容与未来扩展保留 |

与现有字段的兼容关系：

| 新概念字段 | 现有字段 | 迁移原则 |
| --- | --- | --- |
| `targetAssetAmount` | `target` | 先由适配层读取现有字段，不立即改存储键 |
| `monthlyLivingCost` | `livingCost` | 先由适配层映射，不改现有退休公式 |
| `currentMonthlySalary` | `salary` | 仍进入现有月可投入计算，不进入被动收入 |
| `currentMonthlySideIncome` | `sideIncome` | 仍按现有主动现金流处理；若要成为半被动收入，需单独建立收入流并防止重复 |

### 5.2 资产现金流字段

```js
holding = {
  id: "holding_001",
  name: "出租房",
  assetType: "real_estate",
  marketValue: 500000,

  producesCashflow: true,
  cashflowType: "rent",
  cashflowFrequency: "monthly",
  cashflowAmount: 1500,
  cashflowStability: "stable",
  cashflowStatus: "current",

  requiresLabor: false,
  liquidityLevel: "low",
  isEmergencyAvailable: false,
  includeInPassiveIncome: true
}
```

字段规则：

| 字段 | 含义 | 约束 |
| --- | --- | --- |
| `producesCashflow` | 该资产当前是否产生现金流 | 为 `false` 时金额按 0 处理，其他现金流字段不参与计算 |
| `cashflowType` | `rent`、`interest`、`dividend`、`pension_received`、`royalty` 等 | 未知类型不能静默归为被动收入 |
| `cashflowFrequency` | `monthly`、`quarterly`、`annual`、`irregular` | 固定频率用于月化；不固定频率需要历史数据 |
| `cashflowAmount` | 对应频率下的当前实际净到账金额 | 不填预计金额；扣除该来源持续发生且不可避免的来源成本后录入 |
| `cashflowStability` | `stable`、`variable`、`unstable` | 只影响风险解释，不乘权重 |
| `cashflowStatus` | `current`、`future`、`ended` | 只有 `current` 可进入当前收入 |
| `requiresLabor` | 是否仍需持续劳动维护 | 为 `true` 时不得进入严格被动收入，应归入半被动或主动 |
| `liquidityLevel` | `high`、`medium`、`low`、`locked` | 用于安全垫资格判断，不决定现金流资格 |
| `isEmergencyAvailable` | 是否明确可在紧急情况下动用 | 与高流动性共同决定是否可计入安全垫 |
| `includeInPassiveIncome` | 是否通过主被动收入纳入校验 | 是模型控制标志，不是绕过类型与状态规则的用户开关 |

旧资产迁移默认值：

```js
{
  producesCashflow: false,
  cashflowAmount: 0,
  cashflowStatus: "current",
  requiresLabor: false,
  isEmergencyAvailable: false,
  includeInPassiveIncome: false
}
```

不能根据资产类型自动推断现有资产正在产生现金流。例如，基金不等于正在分红，房产不等于正在出租。

### 5.3 独立收入流模型

独立收入流用于记录不直接归属于某个持仓的收入，例如版权收入、小程序订阅和课程分成。

```js
incomeStream = {
  id: "income_001",
  name: "小程序会员收入",
  type: "semi_passive",

  amount: 800,
  frequency: "monthly",
  monthlyHistory: [],

  stability: "unstable",
  status: "current",
  requiresLabor: true,
  source: "project",

  includeInPassiveIncome: false,
  includeInSemiPassiveIncome: true
}
```

相比只保存 `monthlyAmount`，保留 `amount + frequency` 能解释年付、季付和不固定收入的来源；标准化后的月金额是派生值，不应覆盖原始输入。

收入类型与纳入规则：

| `type` | 示例 | 主被动收入 | 半被动补充 | 说明 |
| --- | --- | --- | --- | --- |
| `passive` | 当前净房租、已到账债息/股息、正在领取的养老金、稳定版权收入 | 是，需通过校验 | 否 | 必须当前到账且不依赖持续劳动 |
| `semi_passive` | 小程序订阅、自媒体长尾、课程分成 | 否 | 是，需通过校验 | 必须单独标注维护依赖和稳定性 |
| `active` | 工资、兼职、接单 | 否 | 否 | 属于劳动收入 |
| `one_off` | 奖金、卖资产、红包 | 否 | 否 | 不代表稳定月度能力 |

### 5.4 防重复计算契约

同一笔现金流只能有一个权威来源：

- 由具体资产产生的收入记录在对应 `holding`。
- 不直接归属于持仓的收入才记录为独立 `incomeStream`。
- 标准化后为每笔收入生成 `originKey`，例如 `holding:holding_001:rent` 或 `stream:income_001`。
- 聚合时若出现重复 `originKey`，返回警告并只采用权威来源；不能简单相加。
- 现有 `sideIncome` 与新增收入流可能描述同一笔收入。迁移期默认仍把 `sideIncome` 视为主动收入；用户建立独立收入流时，页面必须提示避免重复录入。

### 5.5 保障账户的当前与未来状态

现有保障字段中的 `estimatedMonthlyBenefit` 表示预计退休后月领，不等于当前已经领取。未来要增加明确状态，例如：

```js
benefit = {
  estimatedMonthlyBenefit: 3000,
  receivingStatus: "future", // "current" | "future" | "ended"
  currentMonthlyReceived: 0
}
```

只有 `receivingStatus === "current"` 且 `currentMonthlyReceived > 0` 的金额，才可能进入当前完全被动收入。公积金余额、未领取养老金和未来年金只能作为未来支持。

房贷冲还贷是指定用途的支出抵扣。它应减少对应的当前房贷支出，不能同时作为被动收入再加一次，否则会产生双重改善。

## 6. 资产现金流分类体系

现金、基金、债券、商品等现有资产类型继续用于资产归类和估值。新体系是第二维度，回答“该资产目前是否产生可用于生活的现金流”。

### 6.1 存量资产

定义：有市值，但当前不直接产生可用于生活的现金流。

示例：黄金、自住房、不分红股票、不出租房产、只依赖价格变化的基金。

产品文案：

> 这项资产具有当前价值，但目前不产生可用于生活的现金流，主要依赖未来出售或价格变化，因此不计入当前现金流退休率。

### 6.2 弱现金流资产

定义：当前产生少量现金流，但对目标生活成本的覆盖有限。

示例：活期存款、货币基金、低息理财、部分债券基金。是否产生“当前收入”必须以实际到账为准，不能根据产品名称推断。

产品文案：

> 这项资产正在产生少量现金流，但对目标生活成本的覆盖仍有限。页面展示实际到账金额，不把预期收益率换算为当前收入。

### 6.3 强现金流资产

定义：当前持续产生较稳定、可用于生活的现金流。

示例：净房租、已到账股息、债券利息、正在领取的养老金或年金、稳定版权收入。

产品文案：

> 这项资产正在较稳定地产生可用于生活的收入，是当前现金流退休率的主要来源。稳定不等于保证，金额仍可能变化或中断。

### 6.4 半被动资产或半被动收入

定义：收入不完全依赖持续工时，但仍需要维护、运营、更新或客户支持。

示例：小程序会员、内容广告、课程分成、自动化工具订阅、持续项目分成。

产品文案：

> 这项收入对持续劳动的依赖较低，但仍需要维护，且稳定性可能变化。它会单独展示，不计入严格现金流退休率。

### 6.5 分类不是产品推荐或收益评级

“弱现金流”“强现金流”只描述用户当前录入的现金流特征，不表示资产好坏，也不构成收益、风险或配置建议。分类不得按某个收益率阈值自动推荐用户更换资产。

## 7. 被动收入与半被动收入边界

### 7.1 完全被动收入的必要条件

一笔收入只有同时满足以下条件，才进入主现金流退休率：

1. 当前已经发生，不是未来预计。
2. 金额基于实际净到账或可核验的当前合同现金流。
3. 可用于支付生活成本，不是锁定余额或仅限特定用途的账面权益。
4. 不需要用户持续投入主要劳动才能获得。
5. 不是出售本金、奖金或其他一次性流入。
6. 没有和其他字段重复记录。
7. 通过 `includeInPassiveIncome` 的模型校验。

### 7.2 半被动收入的判断

符合以下任一情况，应优先标记为半被动，而不是完全被动：

- 需要持续更新内容、维护软件或提供客户支持。
- 收入显著依赖个人品牌活跃度或持续运营。
- 停止维护后，收入预计会较快下降。
- 来源不固定、波动较大，但已有实际历史收入。

半被动收入可以展示其月化金额、稳定性和“含半被动收入覆盖率”，但不得影响主退休状态。

### 7.3 不固定收入

不固定收入不能用“最好月份”或单次金额直接月化。首期采用以下规则：

- 有完整近 12 个自然月记录时，使用 12 个月实际净到账总额除以 12，零收入月份必须保留。
- 历史不足 12 个月时，按已覆盖的连续自然月计算，并标记“历史不足 12 个月”。
- 只有零散单次记录、无法确定观察期时，返回“暂不可月化”，不进入主指标。
- 历史平均只表示已发生收入，不代表未来保证。

### 7.4 预期投资收益不等于当前被动收入

以下内容一律不进入当前月被动收入：

- 按资产市值乘以预期年化收益得到的理论收入。
- 未实现的资产价格上涨。
- 预计但尚未宣告或到账的分红、利息。
- 历史回测收益。
- 卖出资产得到的本金或价差。

## 8. 计算函数设计

所有函数应设计为纯函数，不读取本地存储、不修改输入、不包含页面文案。异常结果使用统一结果信封：

```js
{
  ok: true,
  value: 800,
  reason: null,
  warnings: [],
  provenance: []
}
```

不可计算时返回 `ok: false` 和稳定原因码，数值使用 `null`，避免把缺失误显示为 0。

### 8.1 `normalizeIncomeStream(stream)`

**输入**：一个资产现金流或独立收入流的标准化候选对象。
**输出**：统一收入流，包含 `originKey`、类型、月化金额、当前状态、劳动依赖、稳定性、纳入资格、错误与警告。
**逻辑**：校验枚举和金额；固定频率调用 `annualizeToMonthly`；不固定收入按连续历史月均值；依据 `status`、`type`、`requiresLabor` 决定严格或半被动资格。
**边界**：空对象、未知类型、未知频率、负数、NaN、未来收入、结束收入、历史区间不明、纳入标志与类型冲突。冲突时以严格规则为准并返回警告。
**测试**：必须。它是所有后续计算的入口。

### 8.2 `annualizeToMonthly(amount, frequency, options = {})`

**输入**：非负金额、频率和可选历史信息。
**输出**：月化金额结果。
**逻辑**：

```text
monthly   -> amount
quarterly -> amount / 3
annual    -> amount / 12
irregular -> sum(continuousMonthlyHistory) / coveredCalendarMonths
```

**边界**：负数、NaN、未知频率返回不可用；金额 0 是有效值；不固定收入缺少连续观察期时不可计算。
**测试**：必须，覆盖精度、零值和历史不足 12 个月的警告。

### 8.3 `getMonthlyPassiveIncome(holdings, incomeStreams)`

**输入**：持仓数组和独立收入流数组。
**输出**：严格月被动收入总额、明细、排除明细、警告和来源键。
**逻辑**：把有现金流的持仓和独立收入流标准化；只累加 `type === "passive"`、当前有效、无需持续劳动且通过纳入校验的记录；按 `originKey` 去重。
**边界**：空数组返回 0；坏记录被排除并报告；半被动、主动、一次性、未来支持和预期收益均不累加。
**测试**：必须，尤其测试重复来源和错误纳入标志不能绕过规则。

### 8.4 `getMonthlySemiPassiveIncome(incomeStreams)`

**输入**：独立收入流数组；未来若允许资产产生半被动收入，可扩展为与上一个函数相同的输入契约。
**输出**：月半被动收入总额、明细和警告。
**逻辑**：只累加 `semi_passive`、当前有效且通过半被动纳入校验的记录。
**边界**：不得把该结果传入主现金流退休率；劳动依赖信息缺失时默认不纳入并要求确认。
**测试**：必须，验证单独标注和与主被动收入互斥。

### 8.5 `getCashflowRetirementRate(monthlyPassiveIncome, monthlyLivingCost)`

**输入**：非负严格月被动收入和已由调用方选定口径的正数月生活成本。
**输出**：原始比例、进度显示比例、是否有盈余和原因码。
**逻辑**：`rawRate = income / cost`；`displayProgress = min(rawRate, 1)`。
**边界**：分母缺失或小于等于 0 时不可用；收入缺失、负数或 NaN 时不可用；结果允许大于 1。
**测试**：必须，覆盖 0%、13.3%、90%、100% 和超过 100%。

### 8.6 `getLaborDependenceRate(cashflowRetirementRate)`

**输入**：有效的原始现金流退休率。
**输出**：`max(0, 1 - rate)`。
**逻辑**：作为主指标的反向解释，不重新读取收入。
**边界**：输入不可用时返回不可用；负率视为非法输入；超过 100% 时返回 0。
**测试**：必须，防止负劳动依赖率。

### 8.7 `getRunwayMonths(liquidAssets, monthlyLivingCost)`

**输入**：保守筛选后的可动用资产总额和当前必要月支出。
**输出**：安全垫月数。
**逻辑**：`liquidAssets / monthlyLivingCost`。
**边界**：分母小于等于 0 时不可用；资产 0 返回 0；锁定或未明确可动用的资产应在调用前排除；不自动向上取整。
**测试**：必须，覆盖资产筛选和小数月展示。

### 8.8 `getPassiveIncomeGap(monthlyPassiveIncome, monthlyLivingCost)`

**输入**：严格月被动收入和选定的目标月生活成本。
**输出**：`gap` 与 `surplus`。
**逻辑**：

```text
gap = max(0, cost - income)
surplus = max(0, income - cost)
```

**边界**：分母无效时不可用；超过 100% 时缺口为 0、盈余为正。
**测试**：必须。

### 8.9 `getRetirementStatus(profile, holdings, incomeStreams, options = {})`

**输入**：用户目标、持仓、独立收入流和由适配层提供的当前可动用资产、当前必要支出及保障状态。
**输出**：统一、可供 `overview-model` 消费的结果：

```js
{
  metrics: {
    cashflowRetirementRate,
    cashflowRetirementRateDisplay,
    assetRetirementRate,
    runwayMonths,
    laborDependenceRate,
    passiveIncomeGap,
    passiveIncomeSurplus,
    monthlyPassiveIncome,
    monthlySemiPassiveIncome,
    combinedCoverageRate
  },
  status: {
    code,
    label,
    range
  },
  denominator: {
    amount,
    source // "targetMonthlyLivingCost" | "monthlyLivingCost"
  },
  warnings: [],
  provenance: []
}
```

**逻辑**：选择分母；聚合严格与半被动收入；计算指标；只用严格现金流退休率判定状态；汇总所有警告和来源。资产退休率应调用或接收现有公式结果，而不是复制一份新公式。
**边界**：部分指标不可用时保留其他可用指标；不能因为现金流分母缺失而抹掉资产退休率；不能让未来养老金进入主收入。
**测试**：必须，包括完整集成用例和各子函数结果一致性。

## 9. 退休状态分级

状态只由原始严格现金流退休率判定：

| 状态码 | 名称 | 条件 | 产品表达 |
| --- | --- | --- | --- |
| `survival_dependent` | 生存依赖期 | `< 10%` | 当前生活成本主要仍依赖劳动收入 |
| `cashflow_seed` | 现金流萌芽期 | `>= 10%` 且 `< 30%` | 被动收入已开始承担一小部分目标生活成本 |
| `semi_free` | 半自由期 | `>= 30%` 且 `< 60%` | 已形成一定现金流选择权，但劳动收入仍是重要支柱 |
| `near_retirement` | 准退休期 | `>= 60%` 且 `< 90%` | 工资不再是唯一支柱，仍需检查缺口和稳定性 |
| `cashflow_retirement` | 现金流退休期 | `>= 90%` | 已接近覆盖目标生活成本，具备现金流基础，不等于可以直接辞职 |

### 9.1 为什么不到 100% 仍有意义

10%、30% 和 60% 都对应真实选择权的变化：被动收入可以吸收一部分基础支出、降低收入中断压力、减少对单一工资来源的依赖。产品价值不应只有“达标/未达标”两个状态。

### 9.2 为什么以 90% 作为接近覆盖阈值

90% 表示目标生活成本的绝大部分已由严格被动收入覆盖，剩余缺口相对较小，适合作为产品阶段里程碑。但它不是统计学安全线，也不是监管或行业标准。生活成本估计误差、收入入账周期和金额波动都可能使 90% 与 100% 在短期内互相变化。

### 9.3 如何避免“达到后即可辞职”的误解

状态卡附近固定展示：

> 该状态基于你输入的当前收入和目标生活成本，只反映现金流覆盖，不代表辞职或退休建议。结果未完整覆盖通胀、税费、医疗、家庭责任、收入中断、政策变化和市场风险。

即使达到或超过 100%，也只能表达“当前录入现金流覆盖了当前目标成本”，不能表达“永久安全”。

## 10. 页面改版方向

本节只定义信息层级和文案，不实现 UI。

### 10.1 首页：一主三辅四率面板

展示顺序：

1. 现金流退休率：大卡、第一视觉层级。
2. 资产退休率：现有存量积累进度。
3. 安全垫月数：短期韧性。
4. 劳动依赖率：主指标的反向解释。

主文案示例：

> 你的资产和已形成的被动收入，目前每月约能替你承担 13.3% 的目标生活成本。剩余 86.7% 仍需要劳动收入或其他资金来源支持。你已经开始形成现金流，但还没有覆盖大部分目标生活成本。

补充展示：

- 本次分母：“按目标生活成本 6,000 元/月计算”。
- 严格月被动收入及来源数量。
- 含半被动收入覆盖率，明确“补充观察，不参与状态判定”。
- 数据缺失时显示缺少的具体输入，不伪造 0%。
- 超过 100% 时显示真实比例和每月盈余，进度环封顶 100%。

### 10.2 资产页：增加现金流属性

资产卡片建议展示：

```text
资产名称：出租房
当前市值：500,000 元
月现金流：1,500 元
现金流类型：净房租
当前状态：正在到账
稳定性：较稳定
劳动维护：无需持续劳动
是否计入严格被动收入：是
```

无现金流资产文案：

> 该资产目前不产生可用于生活的现金流，主要依赖未来出售或价格变化，不计入当前现金流退休率。

页面不能把“未填写现金流”解释成“该资产一定没有收益”，应明确这是当前录入状态。

### 10.3 保障页：当前现金流与未来支持分区

**当前现金流**：正在领取的养老金、正在领取的年金、当前实际收到的补贴等。满足严格规则后才能进入当前被动收入。

**未来支持**：尚未领取的养老金、公积金余额、企业年金、职业年金等。只展示未来支持，不进入当前被动收入。

固定说明：

> 养老金、公积金和年金数据来自用户输入，仅用于展示和解释性估算，不代表官方待遇测算。尚未开始领取的金额不会计入当前现金流退休率。

### 10.4 路线页：五阶段现金流路线

| 阶段 | 目标 | 主解释 |
| --- | --- | --- |
| 1. 安全垫阶段 | 可动用资产覆盖约 6–12 个月当前必要支出 | 先建立短期抗风险能力 |
| 2. 本金积累阶段 | 资产持续积累，形成未来现金流的本金基础 | 资产退休率仍用于解释这一阶段 |
| 3. 现金流萌芽阶段 | 严格被动收入覆盖 10%–30% | 资产开始承担一部分生活成本 |
| 4. 半自由阶段 | 严格被动收入覆盖 30%–60% | 已形成一定选择权 |
| 5. 选择权阶段 | 严格被动收入覆盖 60%–90% 以上 | 工资不再是唯一支柱，仍非辞职建议 |

“安全垫 6–12 个月”和各现金流区间是产品解释框架，不是对个人的资产配置建议。

### 10.5 拖累项页：增加被动收入负担解释

保留现有“这笔支出可能让退休时间推迟多久”，同时增加：

> 这笔支出吃掉了多少当前被动收入？

示例一：

```text
你的房租是 3,000 元/月。
当前严格被动收入是 800 元/月。
你的全部严格被动收入只能覆盖房租的 26.7%。
```

示例二：

```text
一台 6,000 元的手机，相当于当前 7.5 个月的严格被动收入。
```

边界：

- 被动收入为 0 时，不执行“支出 / 被动收入”，显示“当前尚无可用于覆盖该支出的被动收入”。
- 一次性支出使用“相当于多少个月被动收入”；月度支出使用“被动收入可覆盖该支出的多少”。
- 文案只做换算，不评价消费是否正确，不诱导焦虑。

## 11. 测试方案设计

后续测试文件建议为 `tests/core/passive-income-model.test.js`，但本阶段不创建测试文件。

### 11.1 标准化与月化

| 场景 | 输入示例 | 预期 |
| --- | --- | --- |
| 月收入 | 1,200 / monthly | 1,200/月 |
| 季度收入 | 3,600 / quarterly | 1,200/月 |
| 年收入 | 14,400 / annual | 1,200/月 |
| 不固定完整历史 | 近 12 月总额 12,000，含零收入月 | 1,000/月，并保留零收入月 |
| 不固定短历史 | 连续 4 月总额 2,000 | 500/月，并提示历史不足 12 月 |
| 不固定无观察期 | 单笔 2,000 | 不可月化，不纳入 |
| 零收入 | 0 / monthly | 有效结果 0 |
| 非法收入 | -1、NaN | 不可用并返回原因码 |
| 未知频率 | `weekly_guess` | 不可用，不静默猜测 |

### 11.2 收入边界

- 当前净房租可计入严格被动收入。
- 需要持续运营的小程序订阅只计入半被动收入。
- 工资、兼职和接单不计入被动或半被动收入。
- 奖金、卖资产和红包不计入稳定月收入。
- `includeInPassiveIncome: true` 不能让 `semi_passive`、`active`、`one_off` 绕过规则。
- 未来养老金、未来年金和公积金余额不计入当前被动收入。
- 已明确正在领取的养老金可按实际当前月领进入严格被动收入。
- 预期收益率乘以资产市值得到的数字不计入。
- 未到账分红和未实现涨幅不计入。
- 同一来源同时出现在资产与收入流时只计一次并返回警告。

### 11.3 指标与阈值

- `800 / 6000` 得到约 `0.133333`，显示 13.3%。
- 劳动依赖率显示 86.7%。
- 现金流退休率 90% 正确进入 `cashflow_retirement`。
- 29.999%、30%、59.999%、60%、89.999%、90% 的边界无重叠、无空档。
- 现金流退休率 125% 时原始值为 125%、进度为 100%、劳动依赖率为 0%、缺口为 0，并展示盈余。
- 月生活成本为 0、负数、NaN 或缺失时现金流退休率不可用。
- 目标月生活成本有效时优先采用；缺失时回退当前月生活成本。
- 两个生活成本都无效时，资产退休率等其他独立指标仍可返回。
- 安全垫只包含明确可动用资产，锁定资产不进入。

### 11.4 迁移与兼容

- 旧资产没有现金流字段时按无当前现金流迁移，不改变市值、成本、行情和分类字段。
- 迁移函数幂等：多次迁移不重复添加或改变用户数据。
- 旧 `target`、`livingCost`、`salary`、`sideIncome` 可经适配层读取。
- 现有 `simulate` 与 `progressFromAssets` 在未接入新页面前结果不变。
- 当前保障账户的 `estimatedMonthlyBenefit` 不会被误认为正在领取。
- 新结果接入 `overview-model` 后，页面不再自行重复计算比例。

### 11.5 文案与页面契约

- 主指标明确使用“完全被动收入”。
- 半被动收入必须有单独标签和维护提示。
- 90% 与 100% 状态均显示“不代表辞职建议”。
- 缺失数据不显示伪造的 0%。
- 超过 100% 的进度组件不溢出，但文本保留真实值。
- 拖累项在被动收入为 0 时不显示无限月份。

### 12.1 必须持续保持的边界

1. 本工具不构成投资建议。
2. 本工具不推荐任何金融产品。
3. 本工具不承诺收益或退休结果。
4. 本工具不预测市场。
5. 本工具不建议用户买入或卖出任何资产。
6. 历史收益和预期收益不能等同未来收益。

### 12.2 就近提示原则

风险说明不能只放在隐私或法律页：

- 现金流退休率旁提示计算口径和非辞职建议。
- 半被动收入旁提示仍需维护。
- 未来保障旁提示不代表官方待遇测算。
- 历史或预期收益旁提示不代表未来收益，且不进入当前被动收入。
- 90% 和超过 100% 的状态旁提示覆盖不等于永久安全。

### 12.3 模型没有覆盖的因素

首期模型没有完整覆盖税费、通胀、医疗支出、家庭责任、收入期限、空置、违约、政策变化、汇率、资产处置成本和极端市场波动。缺少这些因素不妨碍指标用于自我复盘，但必须限制产品结论强度。

## 16. 最终结论

### 16.1 八项明确决策

1. **被动收入模型应该成为《退了吗》的新核心吗？**
   是。更准确地说，“当前严格被动收入对目标生活成本的覆盖能力”应成为第一解释维度。

2. **原来的资产退休率应该保留吗？**
   是。它继续解释本金积累和目标资产进度，但从唯一核心指标降为辅助指标，现有公式保持不变。

3. **现金流退休率应该放在首页第一位吗？**
   是。首页采用一主三辅：现金流退休率第一，随后是资产退休率、安全垫月数和劳动依赖率。

4. **养老金、公积金应该直接计入当前被动收入吗？**
   不能一概计入。只有已经开始领取、当前实际到账且可用于生活的养老金或年金，才可能计入；未领取养老金、公积金余额和未来年金只属于未来支持。指定用途的冲还贷应减少对应支出，不能重复算作收入。

5. **半被动收入应该单独标注吗？**
   是。它不进入主现金流退休率和退休状态，可作为补充覆盖率单独展示。

6. **预期投资收益能算作当前被动收入吗？**
   不能。只有当前实际到账并通过严格边界校验的现金流才可以计入。

7. **下一阶段是否应该先写文档，再写测试，再写代码？**
   是。顺序是产品决策文档 → 失败测试与边界测试 → 纯模型实现 → 聚合层接入 → 页面改版。

8. **当前是否应该立刻改代码？**
   不应该。当前先完成微信真机基线和本文决策，避免在验收期间扩大变更面。

### 16.2 最终产品判断

《退了吗》不应再只回答“你有多少钱”或“距离目标资产还有多远”。新的首页核心应回答：

> 你的资产和已形成的被动收入，当前已经替你承担了多少目标生活成本？

这不是把资产存量模型替换成单一现金流模型，而是建立更完整的退休解释框架：

- 现金流退休率解释当前覆盖能力。
- 资产退休率解释本金积累进度。
- 安全垫月数解释短期韧性。
- 劳动依赖率解释尚需劳动支持的比例。
- 半被动收入和未来保障作为单独层级，提供信息但不抬高主指标。

因此，本次重构的正确方向是：**现金流覆盖能力成为产品核心，资产存量进度继续保留，二者分层呈现、口径透明、结论克制。**
